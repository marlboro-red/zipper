# In-process 7z reader

Zipper reads 7z archives with its own Rust reader. It sends a file here when it starts with the 7z signature, or when it is a [self-extracting 7z](#self-extracting-7z). Every 7z goes to the reader, including damaged and unsafe ones. When a folder uses a method the reader does not decode, the reader refuses the archive by the method's name before anything is extracted.

## Supported archives

The reader decodes these methods:

- LZMA and LZMA2, through Zipper's own decoder in `src/lzma.rs`. It reads every `lc`, `lp` and `pb` that LZMA allows, including the `lc=8` that liblzma refuses. As in 7-Zip, an LZMA stream must end at its declared size. No match may cross that size, and an end marker must follow unless the range coder ends clean there. An LZMA stream cut before its 5 starting bytes is refused, even one that decodes to nothing. An LZMA2 stream may stop after a whole chunk without its end marker, but not inside a chunk. 7-Zip accepts that in a data folder, but refuses it in a BCJ2 branch or an encoded header, which the reader still accepts. `tests/data/7z-hostile` holds an archive of each case, and the test checks 7-Zip's verdict on each.
- Unused packed bytes after an LZMA or LZMA2 stream are not checked, though 7-Zip refuses them. The folder's size and CRC still bound every byte written.
- Copy, Deflate, Deflate64, BZip2 and PPMd. A PPMd model counts its full size against the decoder budget, because the decoder allocates it at the start. A PPMd folder must end exactly at its packed size. Unlike 7-Zip, Zipper does not check that the PPMd range coder ends in a clean state, because the decoder crate keeps that state private. The folder's size and CRC still bound every byte written. Each BZip2 stream after the first must bring 4 KiB of output, as in the [single compressed file reader](stream-reader.md).
- Unused packed bytes after a Deflate or Deflate64 stream are not checked. The folder's size and CRC still bound every byte written.
- The x86 (BCJ), ARM, ARM Thumb, ARM64, RISC-V, PowerPC, SPARC and IA-64 branch filters, and the Delta filter, in a chain of up to 4 in front of LZMA or LZMA2. Zipper decodes them itself, with the filters in `src/xz_filters.rs`. Each branch filter leaves its last bytes as they are when the stream ends too early for a whole instruction, as 7-Zip does. The properties follow 7-Zip 26.05. The six older branch filters take none. ARM64 and RISC-V take an optional 4-byte start offset, a multiple of 4 or 2, which 7-Zip writes for `-m0=ARM64:4096`. Delta takes one byte, the distance less one. Other properties are refused as an unsupported method, as 7-Zip refuses them.
- The Swap2 and Swap4 filters at the output end of any supported folder. Each reverses every whole group of 2 or 4 bytes and leaves a shorter tail as it is, as 7-Zip does. A swap with property bytes is refused, as 7-Zip refuses it.
- The unpack size of a coder inside a chain is not checked, so a chain whose inner sizes disagree with the folder's can be accepted where 7-Zip reports a data error. The folder's size and CRC still bound every byte written.
- BCJ2, the x86 filter with four input streams, decoded by Zipper's own port of the public-domain LZMA SDK decoder. Each of its four inputs is a chain of the methods above, or a packed stream read as is. Every coder and packed stream in the folder must feed exactly one input. A folder holds at most 8 coders, which an encrypted BCJ2 folder fills with BCJ2, its three coders and an AES coder on each packed stream. Each input and each chain's decoder must end exactly where BCJ2 stops reading. As in 7-Zip, a branch marked as converted with fewer than 4 bytes of output left is refused. The four chains reserve their decoders and buffers together, and a BCJ2 folder that needs more than the 2 GiB budget is refused. Each of the four inputs is read through a buffer of up to 1 MiB, inside the 2 MiB each branch reserves. The decoder copies the main stream from that buffer a slice at a time, up to the next E8, E9 or 0F 8x opcode, and decodes a branch bit only at that opcode. A test compares it with the earlier byte-at-a-time decoder on random and encoded streams split at every offset. The [BCJ2 record](../../benchmarks/native-7z/bcj2-buffered-branches/README.md) times the buffered branches before this change.

- AES-256 encryption, 7-Zip's `7zAES` method, in every folder and in an encrypted header, as [Encryption](#encryption) describes.

It reads solid and non-solid archives, solid blocks, compressed and plain headers, and archives that 7-Zip and libarchive write. It extracts files, empty files, folders and symlinks that stay inside the destination. On Windows it creates links as the [ZIP reader](zip-reader.md#symlinks) does.

The reader does not support these features:

- A byte-swap filter after another filter, a coder above BCJ2, other coders with several streams, and a PPMd model larger than the 2 GiB decoder budget. These are refused too.
- AES that is not the coder next to the packed stream, which 7-Zip never writes. This is refused too.
- Anti-items, which delete files during an update, external data and additional header streams.
- Windows reparse points, devices and FIFOs.
- Names with a backslash, which Windows reads as a separator and Unix as part of the name.

## Self-extracting 7z

A self-extracting 7z is an executable stub followed by a 7z archive. Every offset in a 7z counts from its signature, so the archive reads the same after any stub. The reader looks for the signature only when the file starts with `MZ`, `\x7FELF` or one of the Mach-O magic numbers. It reads the archive only when the stub before it passes the stub check in the [ZIP reader](zip-reader.md#self-extracting-zip), which both readers share. The 7z signature must start exactly where the furthest file range the executable's headers name ends, the overlay that 7-Zip opens, and no range may reach past it. A 7z elsewhere, such as one a self-extracting ZIP stores, is left to the ZIP reader when a ZIP end record ends the file, and refused otherwise. 7-Zip searches any file, but searching every unrecognized file would read 8 MiB of each gzip or ZIP self-extractor that reaches this reader.

The signature must start within the first 8 MiB, at offset 8,388,608 or before. 7-Zip 26.05 on macOS opens an archive whose signature starts at that offset and not one byte past it. Each signature found there counts only when its start header has version 0 and its CRC matches. When two signatures pass, the file holds two archives, and the error names both offsets. That includes a stored 7z inside the first 8 MiB of the archive itself. A start header that fails its check is refused as a 7z signature in the stub. The archive may be followed by other bytes, as a signed installer is. A ZIP end record in the last 64 KiB and 22 bytes of the file is refused, because Python and bsdtar would then read a ZIP. That includes a ZIP the 7z stores near its end. The ZIP reader refuses a 7z signature in a ZIP's prefix, so a file is never read as the other format.

`7zz a -sfx` fails on macOS, which ships no SFX module. So `tests/self_extracting.rs` builds each self-extractor by hand, from a generated PE, ELF or Mach-O stub and six corpus and parity archives. That includes BCJ2, a plain header, links and bsdtar's output. Stubs run from 300 bytes to exactly 8 MiB. Each must extract the tree the archive gives alone, and the tree 7-Zip extracts when it is installed. A signature 1 byte past the limit, an archive after a shell script and two archives are refused. So are an archive followed by a ZIP, after a ZIP in the stub, or after a damaged start header. Each denied signature and a stub whose header is not whole are refused too. A 7z with a method the reader does not decode is refused after a clean stub and after a stub that holds a CAB, and never reaches 7-Zip.

## Metadata

The reader restores permission bits and modification times the way the [ZIP reader](zip-reader.md#supported-archives) does. Unix modes come from the high 16 bits of the 7z attributes, which 7-Zip and libarchive write on Unix. An archive without them gives files the default mode, and read-only files mode `0o444` before the umask. Folder times and modes apply after their contents are written.

## Encryption

The reader decrypts AES-256 in process, with the password from `--password`, the prompt, or `ReadOptions::password` and `ExtractOptions::password` in the library. It follows `7zAes.cpp` in 7-Zip 26.05:

- The key is SHA-256 over 2^n rounds of the salt, the password in UTF-16LE and a 64-bit little-endian round counter. 7-Zip writes n = 19 and no salt. A password must be UTF-8, which the reader turns into UTF-16, with surrogate pairs for characters past U+FFFF, as 7-Zip 26.05 does on macOS. The power 63 takes the salt and password as the key without hashing, as 7-Zip does.
- The properties hold the power and the salt and IV sizes, up to 16 bytes each. The IV is padded with zeros. Properties whose sizes do not add up are refused. A power above 24, 7-Zip's limit, is refused before any key is derived. 7-Zip accepts a larger power when the properties are one byte, and would then hash for days. Each key is derived once per salt and power and shared by every folder that uses it.
- The data is AES-256-CBC. The AES coder must be the coder next to the packed stream, in a plain chain or in any BCJ2 branch. Its packed stream must be its decrypted size rounded up to whole 16-byte blocks. The decrypted bytes feed the rest of the chain, so every method and filter above reads encrypted folders.
- 7z has no password check, so a wrong password is found by its effect. In an encrypted header it is found when the decoded header fails its CRC or its decoder. In data it is found by the decoder or the file and folder CRCs. Either way the error says the password is wrong or the data is damaged, as 7-Zip does, and nothing is published. An encrypted header without a CRC, and an encrypted folder whose files and folder have no CRC, are refused, because a wrong password would go unnoticed.
- Without a password, an encrypted header fails at once with `native_7z::PasswordNeeded` and `header: true`, and a selected encrypted folder fails before staging with `header: false`. A selection that reads no encrypted folder needs no password, and `zipper list` reads an archive with a plain header without one.
- The decoder budget counts the 64 KiB decryption buffer of each encrypted folder or branch. An encrypted LZMA2 folder decodes on one thread, because the segment split reads chunk headers from the packed bytes.
- Zipper keeps the password, the UTF-16 copy and the keys in memory that is cleared when the read ends, and clears the stack area that key derivation used. No error names the password.

`tests/encrypted_7z.rs` holds 26 archives from `7zz` 26.05 in `tests/data/encrypted-7z`. They cover LZMA2 at `-mx=1`, 5 and 9, LZMA, PPMd under a plain and an encrypted header, BZip2, Deflate, Deflate64 and Copy. They also cover BCJ, BCJ2, ARM64, Delta and Swap4, and solid, non-solid and solid-block layouts. The header is encrypted in some and plain in others, and one has a header that is encrypted but not compressed. One uses an empty password, and two a Unicode one with a character past U+FFFF. Each must extract the tree 7-Zip gave, at one thread and the default. With a wrong password, an empty one or none, each fails and leaves an existing destination unchanged and no staging folder. Archives built in the test cover every salt and IV size and the power 63, and 7-Zip must extract each to the same bytes. Others refuse malformed properties, as 7-Zip does, and a power past 24 in the data or the header within seconds. One test fails decryption at every point it can fail, and each failure leaves the destination unchanged. The points are no password, a wrong one, no CRC, packed sizes that are not whole blocks, a flipped bit in every encrypted byte and a cut at every length. Another builds an encrypted folder whose packed bytes are themselves a valid LZMA2 stream, and checks that no thread count splits them into segments. A Kani proof covers the property parser for every input of up to 34 bytes. A unit test compares it with a transcription of 7-Zip's parser on every first two bytes and length.

## Safety checks

The reader checks the whole archive before it publishes anything, and it publishes nothing on failure:

- Both header CRCs, every file CRC and every folder CRC.
- Names are safe archive paths, unique, and never used both as a file and as a folder. Symlink targets stay inside the destination and are created after every file.
- Packed streams lie before the header and do not overflow. Folder and file sizes agree, and a folder holds no data beyond its files. A folder with no output is refused, because 7-Zip never writes one.
- Counts are bounded by the bytes the header has left, and the header is at most 64 MiB, decoded or not. A header that lists the full 1,000,000 entries can still take a few hundred MiB of memory to hold.
- An LZMA dictionary is cut to the size of the folder's output, so a hostile dictionary size does not allocate memory. Decoders running at once share a 2 GiB memory budget. An LZMA or LZMA2 decoder counts its window, its input buffer and its probability tables against it. Each branch filter in a chain counts its 64 KiB buffer, and each Delta filter its 256 bytes of history. The 256 MiB dictionary limit of the [tar reader](tar-reader.md#limits) does not apply to 7z. This budget is the 7z reader's only dictionary limit, and a folder that needs more than all of it waits for the whole budget and decodes alone.

`tests/hostile_7z.rs` crafts archives that break each check, and `tests/sevenz_fuzz.rs` mutates the corpus with repaired header CRCs.

## Extraction options

These options work the same way as in the other readers. [Usage](../usage.md#extract-into-an-existing-folder) shows them.

- `Existing::Overwrite`, or `zipper extract --overwrite`, extracts into an existing folder. A rename that fails undoes the ones before it, so the destination keeps what it held.
- `paths`, `include` and `exclude`, or `--path`, `--include` and `--exclude`, select entries, as [usage](../usage.md#extract-selected-paths) describes. Only folders that hold a selected file decode, and each decodes completely, because 7z has no way to skip into a folder and its CRC covers all of it.
- `strip`, or `--strip-prefix` and `--strip-components`, places a folder's contents at the destination root, as [usage](../usage.md#extract-a-folder-at-the-output-root) describes.
- `metadata: Metadata::ContentOnly`, or `--content-only`, writes contents and the execute bit only, as [usage](../usage.md#extract-contents-only) describes.
- `Control` reports progress with both totals known, and stops on the cancel flag.

Folders decode in parallel on their own worker threads, up to `--threads`, largest first. A solid archive has one folder. When that folder uses LZMA2, alone or behind branch and Delta filters, and holds at least 8 MiB, the reader reads the chunk headers and splits the stream where it resets its dictionary. It decodes those segments on up to `--threads` decoders, in order, and the folder's worker runs the filters over their output. The folder's worker decodes the front segment itself, straight into the files, and holds only that segment's dictionary. Each segment behind the front decodes on its own thread and holds its decoded bytes and its dictionary until its turn. The threads' segments and the folder's largest front dictionary together stay within 224 MiB. They count that dictionary even after it is freed, because the allocator can keep freed memory resident. A segment too large for a thread waits until it is the front. A folder whose dictionary needs more than 224 MiB reserves its whole dictionary, because its front segment can hold that much alone. A filtered folder also reserves its filter buffers. A BZip2 folder decodes its blocks on up to one thread fewer than the threads the folder has, in order, as the [single file reference](stream-reader.md) describes. It reserves about 12.3 MiB for each of those threads, 16 at most, and 25.7 MiB beside them. A BZip2 folder on one thread reserves the 25.7 MiB alone. Any other layout decodes on one thread. The [parallel segment measurements](../../benchmarks/native-7z/lzma2-segments/README.md) record the gain. A TLA+ model in `verification/7z-folder-workers/` checks every order of the workers' steps, within a bound, for hangs, budget overruns, folders decoded twice, and a publish after a corrupt folder or a cancel. The `zipper-verify-7z-workers` skill in `.claude/skills/` runs it.

On macOS, a 7z whose selected folders each hold at most one file decodes on at most four folder workers when the extraction would create many small files. That holds when the selected folders hold at least 1,024 regular files and those files average at most 64 KiB. This is the rule the [ZIP reader](zip-reader.md#concurrency) applies, with the same limit. Empty files and folders do not count, because the caller's thread creates them after the workers end. Links and files outside the selection do not count either. The cap also applies to `zipper test`, where each folder's setup costs as much as on extraction. An explicit `--threads N` overrides it, and Linux and Windows have no cap. The [write-path study](../../benchmarks/write-path/study/README.md) measured the default against fixed thread counts on a 12-core Mac, writing to an APFS disk image. Its 10,000 flat tiny files took 409.8 ms at four threads against 568.5 at the default. Its dependency sources took 307.8 ms at four against 293.4 at the default, so the cap of four is not yet measured as a gain on every tree it covers.

In a folder of more than one file, the folder's worker hands each file of at most 1 MiB to up to four writer threads, never more than `--threads`, and goes on decoding. These are the writers the [tar reader](tar-reader.md) uses. The worker still decodes each file and checks its own CRC before the hand-off, so a file that fails that CRC is never written. When only the folder has a CRC, its files are written to the staging folder before the check fails, as on the worker's own path. A file larger than 1 MiB, the file of a one-file folder and every file at `--threads 1` are written by the folder's worker. Each handed-off file takes a whole 1 MiB buffer, and the buffers are reused. So at most 16 files and 16 MiB of buffers wait for the writers across all folders, outside the 2 GiB decoder budget. Each lane queue holds at most 16 files. A failed write, a cancel or a panic in a writer fails the extraction, and nothing is published. Progress counts a handed-off file once its writer has written it. A second TLA+ model in `verification/7z-writer-pool/` checks every order of these steps, within a bound, for hangs, budget overruns, leaked chunks, files written twice, and a publish after a failure or a cancel.

## Reference corpus

`scripts/make_7z_corpus.py` writes 63 archives from 7-Zip and libarchive, over the short and long trees of the tar corpus and a tree of links. It covers each supported method, solid blocks, plain headers and non-solid archives. BCJ in front of LZMA2 and of LZMA, and BCJ2, also run over a tree of x86-like code, so that BCJ2's call and jump streams hold converted targets. BCJ2 appears both in 7-Zip's default layout and with every branch bound to its own LZMA coder. 7-Zip and bsdtar must extract the same tree, and `tests/sevenz_corpus.rs` checks the reader against it, including modes and times. One more archive uses a password. The test checks that the reader refuses it by name without the password, that `zipper::choose_reader` sends it to the reader, and that it extracts with the password. Another holds the short tree with the LZMA setting `lc=8`, which liblzma and so bsdtar refuse. The reader must extract it to the tree 7-Zip extracts from the plain LZMA archive of the same tree. `tests/data/7z-hostile/filter-*.7z` come from 7-Zip 26.05 over trees of code for each filter the corpus lacks, with start offsets, Delta's longest distance and a chain of 4 filters. `tests/hostile_7z.rs` checks that the reader extracts each as 7-Zip does. When 7-Zip is installed, it also checks that each filter decodes any bytes, at every short length, as 7-Zip does, and accepts the same properties. A unit test compares every filter, start offset and Delta distance with liblzma. It covers every length up to 64 bytes and lengths around the 64 KiB buffer, read 1 byte, a random size or a whole buffer at a time.
