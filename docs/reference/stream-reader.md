# Single compressed file reader

Zipper reads a file that holds one gzip, bzip2, xz, zstd, lzip, LZ4, `compress` (`.Z`), LZMA, lzma86, PPMd or Microsoft SZDD stream, and no tar, with its own reader. `zipper extract notes.txt.gz -o out` writes `out/notes.txt`.

## Supported files

- gzip, including several gzip members in a row, which decode as one file.
- bzip2, including several bzip2 streams in a row. Each stream after the first must bring at least 4 KiB of output, because each one costs a block of several MiB to start. A file of many tiny streams is refused. Zipper's own decoder in `src/bzip2.rs` finds each block by its magic. With more than one thread it decodes the blocks on up to one thread fewer than `--threads`, and on 16 at most. With one thread it decodes each block in place. It passes them on in order and checks every block CRC and stream CRC. A magic inside a block's data ends no block, because the reader accepts a block only where its decoding ends. Each of those threads counts for about 12.3 MiB, with 25.7 MiB beside them, which is also what one thread counts for. That is twice the input of a usual block, the 5.2 MiB a block needs while it decodes, and as much again for memory the allocator keeps after a block. A block of more than 4 MiB of compressed bytes is refused, at every thread count. No bzip2 writer makes such a block. The `bzip2` crate, which read with one thread before, refused some padded code tables that libbzip2 accepts. Zipper's decoder accepts them up to the 4 MiB limit, as libbzip2 does. ZIP entries, xar files and DMG chunks use the same decoder, one block at a time on the thread that reads them. A TLA+ model in `verification/bzip2-blocks/` checks every order of the threads' steps, within a bound, for blocks out of order, a false magic taken as a block, hangs and budget overruns.
- xz, including several xz streams in a row.
- zstd, including several frames in a row and skippable frames between them, decoded by Zipper's own decoder. It checks the content checksum when the frame holds one, and the content size when the header gives one.
- lzip, versions 0 and 1, including several members in a row, decoded by Zipper's own decoder in `src/lzma.rs` one member at a time. 7-Zip does not read lzip. Zero padding after the last member, which bsdtar writes to standard output, is refused as trailing data.
- LZ4 frames, including several in a row and skippable frames between them, decoded by Zipper's own reader. It checks the header checksum, every block checksum and the content checksum the frame holds, and the content size when the frame gives one. Linked blocks reach back 64 KiB into the previous block. A frame that needs a dictionary, and the legacy frame of `lz4 -l`, are refused. Each block is decoded within what is left of the frame's declared content size, so a frame that lies about its size stops at the first byte past it. The block decoder is written from the LZ4 Block Format description. The reader holds one compressed block and one decoded block, each at most the frame's block size of up to 4 MiB, with 16 spare bytes, since it copies 16 bytes at a time. A block's room starts at 64 KiB or four times its compressed size and grows fourfold when its output needs more, so a small block in a frame of 4 MiB blocks takes little memory. Linked blocks add up to 1 MiB of history. 7-Zip does not read LZ4.
- `compress` (`.Z`), in block mode and in the older mode without clear codes, at 9 to 16 bits, decoded by Zipper's own reader. The format has no checksum and no length, so a stream cut at a code boundary, or with data appended, cannot be told from a whole one, as with 7-Zip and gzip. A code the stream has not defined yet is refused. The reader is written from the format as ncompress, BSD `zopen` and gzip's `unlzw` read it, and from the LZW technique of keeping each code's length so its string can be written forwards. Each entry of its 1 MiB code table holds the last piece of its string, up to 8 bytes, with the string's length and the code of the string before that piece. So the reader writes each string forward one 8-byte piece at a time into 128 KiB of output. It reads the 8 codes of a group from one 16-byte load. An input read that fails with `Interrupted` keeps the part of a group it already took, so a caller that retries goes on where it stopped.
- zstd and LZ4 share their skippable frame. When a file starts with one, the reader skips up to 16 of them and lets the next frame decide. So `pzstd` output still reads as zstd, and an LZ4 file that starts with metadata reads as LZ4.
- LZMA in its old `.lzma` form. It has no signature, so a file counts as LZMA only when its name ends in `.lzma`, its first byte is a valid properties byte, and no ZIP, tar or 7z reader claims it first.
- lzma86, the format of 7-Zip's `lzma` tool, which is LZMA with an optional x86 BCJ filter, decoded by Zipper's own LZMA decoder and BCJ filter. It has no signature either. As in 7-Zip, a file of any name counts as lzma86 when its first 16 bytes hold a header 7-Zip accepts and a first LZMA byte of 0. That header has a filter byte of 0 or 1, a properties byte below 225, a dictionary of 1, 2 or 3 times a power of two, and a size below 2^56 or unknown. A known size of 1 or more also needs the next byte's top bit clear. Unlike 7-Zip, Zipper does not decode the start of the stream to decide. So a file such as firmware with a valid header fails with an LZMA error, where 7-Zip says it is not an archive. Several streams in a row decode in order, each with its own BCJ state. Each stream after the first must bring at least 4 KiB of output, as with bzip2.
- PPMd `.pmd` files of var.H, version 7, and var.I, version 8, with the restart or cut-off restore method, decoded by the `ppmd-rust` crate. These are the variants 7-Zip decodes. The stream ends at its end marker with a clean range coder.
- SZDD files from Microsoft's `compress.exe`, such as `SETUP.EX_`, decoded by Zipper's own LZSS decoder. The decoded size comes from the header, at most 2 GiB, the limit of 7-Zip 26.06 and of Windows. 7-Zip 26.05 accepts sizes up to 4 GiB. Zipper follows 7-Zip 26.05, which starts the 4 KiB window as spaces and refuses a copy longer than 16 bytes. 7-Zip 26.06 starts the window's last 16 bytes as zeros and accepts copies of 17 and 18 bytes. Neither case appears in files Microsoft's encoder writes. KWAJ files, the other `compress.exe` form, are not read, because 7-Zip does not read them either.
- Not Base64. A file named `*.b64` that holds only Base64 text is refused, since the Base64 reader was removed on 12 November 2026 for licence reasons, as the [refused formats page](refused.md) records.
- Intel HEX decodes to one file for each run of addresses, which is not one stream, so the [Intel HEX reader](ihex-reader.md) reads it.

`tests/data/stream` holds the lzip and LZ4 files, which 7-Zip's parity corpus cannot hold. `scripts/make_stream_files.py` writes it with bsdtar and checks it with a second decoder. `tests/legacy_streams.rs` writes its lzma86, PPMd and SZDD files itself and checks each against `7zz x`.

Zipper sends a file here when it starts with one of these signatures and the [tar reader](tar-reader.md) finds no tar inside. A tar inside gzip, bzip2, xz, zstd, lzip, LZ4, `compress` or LZMA goes to the tar reader, which extracts its files. A tar inside lzma86, PPMd or SZDD extracts as the `.tar` file, as with 7-Zip.

## Output name

The decoded file is named as 7-Zip names it:

- `.gz`, `.gzip`, `.bz2`, `.bzip2`, `.xz`, `.zst`, `.zstd`, `.lz`, `.lz4`, `.Z` and `.lzma`, in any letter case, are dropped.
- `.tgz`, `.tbz`, `.tbz2`, `.txz`, `.tzst`, `.tpz`, `.tlz`, `.tlz4`, `.taz` and `.tz` become `.tar`.
- Any other extension is dropped, and a name without one gains `~`. So the decoded file never takes the archive's own name, even in the archive's own folder.
- `\` and `:` become `_`, and so do `<`, `>`, `"`, `|`, `?`, `*` and characters below U+0020 on Windows. Trailing spaces are dropped. On Windows each dot or space of the run that then ends the name becomes `_`, so `a .` becomes `a__`. A name left as `.` or `..` becomes `_`, and a name that is still not safe, such as `CON` on Windows, gains a leading `_`.

lzma86 drops the archive's last extension, or adds `~` to a name without one, as 7-Zip does for every format without its own rule.

A PPMd file stores the decoded file's name, which may hold folders. Zipper names the file as 7-Zip 26.05 does. The name ends at its first NUL. Empty, `.` and `..` folders are dropped, and a last part that is empty, `.` or `..` becomes `_`. Each part then loses `\`, `:` and on Windows the other characters above, and on Windows each trailing space or dot becomes `_`. A name that is not UTF-8 has each bad sequence replaced with U+FFFD, where 7-Zip drops it. A file with no stored name takes the archive's name without its last extension.

An SZDD file named with a trailing `_`, such as `SETUP.EX_`, is named as 7-Zip 26.05 names it. The `_` is dropped, and the byte the header stores takes its place when it is printable ASCII. A zero byte means the encoder left the last letter out, so `.bi`, `.dl`, `.ex`, `.km`, `.pd` and `.sy` gain `n`, `l`, `e`, `d`, `f` and `s`, in lower case only. A `/` the header stores becomes a folder whose file is named `_`, as in 7-Zip. Any other name takes the archive's name without its last extension.

A name taken from a PPMd or SZDD header that equals the archive's own name, ignoring ASCII case, gains `~`, where 7-Zip would write over the archive in its own folder. A strip that would leave that name is refused.

A name stored inside a gzip header is ignored, because it could hold a path. A file split into [volumes](zip-reader.md#split-volumes) is named from its first volume's name without `.001`.

## Safety checks

- The output goes to a hidden staging folder and is published only when the whole stream decodes, as with every reader.
- The decoded size must stay within free space, or within `--max-extracted-bytes`, checked while decoding.
- Every decoder checks the checksum its format carries. gzip has a CRC-32, bzip2 has block and stream CRCs, and xz has its check. zstd has a frame checksum when the frame holds one, each lzip member has a CRC-32 and its sizes, and an LZ4 frame has the checksums above when its writer set them. LZMA, lzma86, PPMd and SZDD have no checksum.
- An lzma86 or SZDD stream with a declared size must decode to exactly that size. A copy that would run past it is refused before any of it is written. An lzma86 stream may end with an end marker at its size, as 7-Zip allows.
- An SZDD file must leave the flag bits after its last token clear, as 7-Zip 26.06 requires and 26.05 does not check.
- A PPMd model takes the memory its header names, from 1 to 256 MiB, as the ZIP and 7z PPMd readers do. The `ppmd-rust` crate fills the whole model with zeros when decoding starts, so even a tiny file can use that much memory, where 7-Zip touches only the pages it uses.
- A PPMd file with data after its end marker is refused. 7-Zip extracts the first file of such a file and ignores the rest, which may be a second file that PPMd itself wrote.
- An xz, LZMA or lzip stream with a dictionary larger than the [tar reader's limit](tar-reader.md#limits), 256 MiB, is refused. An lzma86 stream is refused when its window, the dictionary or the declared size if smaller, is larger than 256 MiB. A zstd frame with a window larger than 128 MiB is refused, as the [tar reader](tar-reader.md#limits) refuses it.
- A gzip file is read 1 MiB at a time and decoded into a window of 544 KiB, and each decoded piece is written from that window. Pieces under 64 KiB, such as the members of a file with many small members, are merged in a buffer of that size first. The reader holds no other copy of the data, whatever the file's size. The [gzip and zlib record](../../benchmarks/deflate/gzip-file/README.md) measured the sizes.
- A truncated stream is refused at every length, and data after the last stream is refused, except in `compress`, as above.
- `--path`, `--include` and `--exclude` select the one decoded file by its output name.

## Tests

`tests/hostile_stream.rs` truncates each corpus file at every length, appends trailing data, damages a gzip CRC and caps the output. `tests/parity.rs` checks each corpus file against the tree 7-Zip extracts.

`tests/legacy_streams.rs` writes lzma86 files with 7-Zip's own LZMA and BCJ encoders and with liblzma, PPMd files with the `ppmd-rust` encoders, and SZDD files with its own encoder. Each extracts through `zipper::extract_archive` to the tree `7zz x` extracts, names included. Files with one damaged byte are refused exactly when 7-Zip refuses them, apart from the checks above that 7-Zip lacks. The test also cuts each format at every length and appends trailing data. `every_pseudo_random_stream_decodes_as_the_reference_does_at_every_split` in `src/mslz.rs` compares the SZDD decoder with a separate byte-at-a-time decoder on 20,000 streams, at four input and output splits. Kani proofs under `[legacy-streams]` in `verification/coverage.txt` cover the three header readers, the lzma86 check and the SZDD decoder's window indexing.
