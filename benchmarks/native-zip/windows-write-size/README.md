# Bound native-fast output write size on Windows

Hypothesis: the previously observed Windows large-entry regression comes from
large synchronous output writes, rather than solely from the decoder. Compare
streaming, whole-buffer decoding with one output write, and identical whole-buffer
decoding with 256 KiB output slices. The candidate changes only write size; there
are no additional buffers, copies, threads or checksum changes.

[Experiment 40985992348](https://github.com/marlboro-red/zipper/actions/runs/40985992348)
built source `b48ea32` and an isolated candidate patch. Seven interleaved measured
rounds after warmup, four requested workers, one entry per ZIP. Whole-buffer
readers explicitly use a 128 MiB shared entry-buffer budget so the mixed/random
cases cannot silently fall back to streaming. Every extraction is compared with
the original bytes and complete tree; integrity-only timing also has a separately
verified extraction outside its timed region. Fixtures are generated by
`scripts/make_large_zip_corpus.py` with seed 20261030.

## Windows extraction

| Fixture | Whole-write ms [range] | 256 KiB writes ms [range] | Speedup | Streaming ms | Whole/chunked peak RAM MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Mixed, 61 MiB | 702.86 [630.03–728.91] | 104.65 [104.22–105.50] | 6.72× | 124.16 | 97.12 / 97.12 |
| Compressible, 32 MiB | 193.37 [177.18–231.09] | 35.93 [35.32–36.51] | 5.38× | 33.12 | 35.95 / 35.93 |
| Random, 32 MiB | 229.35 [215.19–263.43] | 37.25 [36.87–37.49] | 6.16× | 45.44 | 67.88 / 67.88 |

Retain **only on Windows**. These are end-to-end extraction gains against the
old whole-buffer path, not universal speedups over streaming. After the change,
whole-buffer mode beats streaming on mixed/random data in this run, while
streaming still wins on compressible data and uses approximately 4 MiB RAM.
The default shared budget stays 64 MiB on Windows: mixed/random inputs here still
stream unless the user increases it. The compressible input fits the default
budget, so that gain applies without increasing the budget.

Integrity-only medians (whole-buffer / streaming) were 86.61 / 88.32 ms for mixed,
26.06 / 23.04 ms for compressible and 27.33 / 20.03 ms for random data. The large
whole-buffer extraction penalty is absent without output writes. These timings
include input reads, allocation, decoding and CRC checks; they are not isolated
codec throughput. No cache flushing or extraction fsync is requested. This
experiment identifies a beneficial write size on this hosted Windows system,
not a proven kernel or antivirus cause. Protection settings were not changed.

## Other platforms

Linux whole-write / chunked medians were 91.73 / 92.25 ms (mixed), 28.64 / 28.69 ms
(compressible), and 39.45 / 39.61 ms (random), with overlapping ranges. Streaming
was faster than either whole-buffer path on all three Linux fixtures. Local M5
mixed extraction was 54.64 [50.05–57.91] versus 67.49 [54.95–75.16] ms; ranges
also overlap and no benefit is established. Both platforms retain whole writes.

The production change is conditional on Windows; it executes the same chunk loop
as the measured Windows candidate. Full Rust tests, formatting, Clippy and direct
release byte checks pass. The experiment's Windows release tests exercise chunk
boundaries and final partial chunks through existing large-entry, CRC-failure and
cleanup tests. Validation still completes before buffered output is written, and
failed extraction is never published.

```powershell
# Optional higher-memory mode; the normal Windows default remains 64 MiB.
zipper --zip-engine native-fast --zip-buffer-mib 128 extract files.zip -o restored
```

Reports retain every sample, observed range, memory high-water mark, binary/archive
hash, command and run order. The original candidate patch is kept alongside the
reports; reproduction requires the recorded baseline, before the production
conditional loop was added. Do not multiply this gain by unrelated small-file
reader/cache improvements.
