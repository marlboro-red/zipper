# Windows alpha release versus current source

On Windows, current native-fast extracts a 32 MiB compressible ZIP entry 7.43× faster than native-fast in the published `v0.1.0-alpha.1` executable. That gain removes a native-fast regression. The streaming `native` reader in both builds was faster still, at 27.41 ms in the alpha and 27.55 ms in current source, versus 30.06 ms for current native-fast. Current native-fast is slower on large mixed and random entries that stream, and streaming `native` is slower on random. Small-file results are inconclusive, so this run does not show a universal Windows improvement.

## Question

How does current source compare with the actual downloadable Windows alpha on native-fast ZIP extraction and native-format extraction?

## Setup

[Run 40987906123](https://github.com/marlboro-red/zipper/actions/runs/40987906123) compares the actual downloadable `v0.1.0-alpha.1` executable (source `55bc598`) with source `88bb098` (runtime change through `a248ffd`). The downloaded package SHA-256 is pinned to `7ae62938561a71bf951019cb5395ab3694c116d56c9fc2fa8eb3d8d0ff8e046b`. Both builds use Rust 1.96.0, x86_64-pc-windows-msvc, release optimization, and static CRT.

- Seven interleaved rounds after warmup, on the same Windows Server 2022 runner.
- Four requested workers, identical input archives, and normal memory budgets. No 128 MiB override is applied.
- Every timed extraction is followed by direct comparison of all restored bytes, sizes, and full tree membership.
- No explicit extraction fsync is requested.

The JSON files retain exact commands, executable and archive hashes, individual samples, ranges, and memory.

The `native` and `native-fast` ZIP readers are opt-in. The normal ZIP command still delegates to an external 7-Zip installation. That backend implementation is unchanged and was not benchmarked here.

## Results

### Native-fast ZIP

| Workload | Published alpha ms [range] | Current ms [range] | Interpretation |
| --- | ---: | ---: | --- |
| 1,000 flat files | 369.01 [333.55–1564.48] | 412.16 [338.34–1166.20] | Inconclusive; broad overlapping ranges |
| 1,000 grouped files | 295.92 [262.86–1013.48] | 398.63 [270.73–1238.99] | Inconclusive; broad overlapping ranges |
| 32 MiB compressible | 223.41 [198.52–238.16] | 30.06 [29.47–30.41] | 7.43× faster than alpha native-fast; slower than streaming in both builds |
| 61 MiB mixed | 94.65 [94.12–95.49] | 100.94 [99.95–431.72] | 6.6% slower; separated ranges |
| 32 MiB random | 34.43 [33.70–34.69] | 39.76 [39.41–40.18] | 15.5% slower; separated ranges |

The compressible entry fits the normal whole-buffer eligibility of both builds. Its large gain is consistent with the measured Windows output-write fix. Mixed and random entries exceed the 64 MiB combined compressed and decoded eligibility, so both builds stream them. Their regression is real in this run. Streaming `native` also regresses on random data, from 34.51 to 39.59 ms, with separated ranges.

### Streaming native ZIP

The same run measured the streaming `native` reader on the same archives.

| Workload | Published alpha ms [range] | Current ms [range] | Interpretation |
| --- | ---: | ---: | --- |
| 1,000 flat files | 350.99 [337.97–528.69] | 444.95 [331.67–814.35] | Inconclusive; overlapping ranges |
| 1,000 grouped files | 550.25 [224.38–1371.65] | 479.40 [248.39–1923.82] | Inconclusive; overlapping ranges |
| 32 MiB compressible | 27.41 [26.98–28.11] | 27.55 [26.88–27.89] | No established change; overlapping ranges |
| 61 MiB mixed | 95.04 [93.98–122.29] | 100.35 [99.82–184.21] | Inconclusive; overlapping ranges |
| 32 MiB random | 34.51 [33.65–35.34] | 39.59 [39.27–40.12] | 14.7% slower; separated ranges |

On the compressible entry, streaming in either build beat current native-fast at 30.06 [29.47–30.41] ms, with separated ranges. The 7.43× native-fast gain therefore compares native-fast with itself. It is not a gain over the fastest reader in the alpha.

### Native format

An identical native archive, generated by the released executable, contains the 1,000-file grouped tree. Release extraction took 285.87 [252.52–489.99] ms, and current extraction took 288.93 [237.47–821.72] ms. That is no established speed change. Core native-format and pipeline source files are unchanged since the alpha.

### Memory

| Workload | Current MiB | Release MiB |
| --- | --- | --- |
| Small-file ZIP reader peak | about 5.0–5.2 | 6.2–6.4 |
| Compressible whole-buffer extraction | 35.72 | 36.18 |
| Large entries falling back to streaming | roughly 3.7–3.9 | 4.3–4.4 |
| Native-format extraction, small tree | 4.75 | 4.77 |

## Decision

Investigate the large-entry streaming regression. Do not claim a universal Windows improvement. Do not present the 7.43× native-fast gain as a gain over the alpha's streaming reader. The changed file reader is a candidate cause, not an established diagnosis. These results supersede any inference that the earlier isolated 5–7× Windows write-path gain applied universally against the published release.

The download remains the original alpha. This comparison does not publish a new release.

## Limits

- This is one hosted-runner comparison. Cache state is uncontrolled.
- Small-file timing is especially noisy.
- The run is not evidence about every Windows machine, ZIP layout, or storage device.
- Compression timing was not measured in this comparison.
