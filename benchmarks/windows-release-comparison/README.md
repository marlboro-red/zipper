# Actual Windows alpha versus current source

[Run 40987906123](https://github.com/marlboro-red/zipper/actions/runs/40987906123)
compares the actual downloadable `v0.1.0-alpha.1` executable (source `55bc598`)
with source `88bb098` (runtime change through `a248ffd`). The downloaded package
SHA-256 is pinned to `7ae62938561a71bf951019cb5395ab3694c116d56c9fc2fa8eb3d8d0ff8e046b`.
Both use Rust 1.96.0, x86_64-pc-windows-msvc, release optimization and static CRT.

Seven interleaved rounds after warmup, same Windows Server 2022 runner, four
requested workers, identical input archives, normal memory budgets. No 128 MiB
override is applied. Every timed extraction is followed by direct comparison of
all restored bytes, sizes and full tree membership. Cache state is uncontrolled;
no explicit extraction fsync is requested. Exact commands, executable/archive
hashes, individual samples, ranges and memory are retained in JSON.

## Native-fast ZIP comparison

| Workload | Published alpha ms [range] | Current ms [range] | Interpretation |
| --- | ---: | ---: | --- |
| 1,000 flat files | 369.01 [333.55–1564.48] | 412.16 [338.34–1166.20] | Inconclusive; broad overlapping ranges |
| 1,000 grouped files | 295.92 [262.86–1013.48] | 398.63 [270.73–1238.99] | Inconclusive; broad overlapping ranges |
| 32 MiB compressible | 223.41 [198.52–238.16] | 30.06 [29.47–30.41] | 7.43× faster |
| 61 MiB mixed | 94.65 [94.12–95.49] | 100.94 [99.95–431.72] | 6.6% slower; separated ranges |
| 32 MiB random | 34.43 [33.70–34.69] | 39.76 [39.41–40.18] | 15.5% slower; separated ranges |

The compressible entry fits both builds' normal whole-buffer eligibility. Its
large gain is consistent with the measured Windows output-write fix. Mixed and
random entries exceed the 64 MiB combined compressed/decoded eligibility and use
streaming in both builds. Their regression is real in this run and must be
investigated; do not claim a universal Windows improvement. The changed file
reader is a candidate cause, not an established diagnosis. Streaming `native`
also regresses on random data: 34.51 to 39.59 ms, with separated ranges.

The normal ZIP command still delegates to an external 7-Zip installation. That
backend implementation is unchanged and was not benchmarked here. The `native`
and `native-fast` ZIP readers are opt-in.

## Native format

An identical native archive generated by the released executable contains the
1,000-file grouped tree. Release extraction was 285.87 [252.52–489.99] ms; current
was 288.93 [237.47–821.72] ms. No established speed change. Core native-format and
pipeline source files are unchanged since the alpha. Compression timing was not
measured in this comparison.

## Memory and limitations

Current small-file ZIP reader peak memory was approximately 5.0–5.2 MiB versus
6.2–6.4 MiB in the release. Compressible whole-buffer extraction used 35.72 versus
36.18 MiB. Large entries falling back to streaming used roughly 3.7–3.9 versus
4.3–4.4 MiB. Native-format extraction was 4.75 versus 4.77 MiB on the small tree.

This is one hosted-runner comparison. Small-file timing is especially noisy, and
this is not evidence about every Windows machine, ZIP layout or storage device.
The download remains the original alpha; this comparison does not publish a new
release. Results supersede any inference that the earlier isolated 5–7× Windows
write-path gain applied universally against the published release.
